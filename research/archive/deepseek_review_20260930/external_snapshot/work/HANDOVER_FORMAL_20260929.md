## 二、未解决的两个缺陷：机制已经查清

### 现象

角色从机枪位换回副驾后：**炮塔仍随其视角转动**；双方看到的射击方向不一致；朝向不平滑（0.8.1 之后朝向已开始跟随，但离散）。

### 根因（有日志证据，非推测）

回程（机枪→副驾）**不会产生引擎自己的权威座位 RPC**。

```
去程（副驾→机枪）：seq7  entry_request(4118,4107,4) → accepted     ← 引擎自己发的
回程（机枪→副驾）：只有 snapshot + transition        ← 没有任何 entry/exit request
手动下车时：        exit_request(4118,4107,1,0) → exit_accepted    ← 引擎自己发的
```

**主机被告知"客人挂上了机枪武器"，却从未被告知"卸下了"。** 主机因此持续用客人的视角驱动炮塔；复制回灌又让本地客户端看到同样现象。单人正常，因为没有主机持有这个过期绑定。

### 三次本地改动产生**逐字节相同**的流量（决定性证据）

| 版本 | 改动 | 回程发出的原生消息 |
|---|---|---|
| 0.8.1 | 布尔写 `false` | `snapshot` + `transition` + `authority_owned` |
| 0.8.2 | 再清标志位 `0x2c` | **完全相同** |
| 0.8.3 | 再跑引擎恢复动作 | **完全相同** |

→ **纯本地改动到不了主机**，所以任何数值调整都不可能修好它。

### 另外两个结构性事实

- 正式版 `native.lua` 第 116–128 行与实验包 `transaction.lua` **共用同一套武器卸载代码** —— 缺的那一步从来不在两边；
- 手写换座会让**引擎自己的权威座位记录**与复制出去的状态分叉。0.8.4 实测：我们把角色放到座位 1、也告诉了主机座位 1，但引擎后来自己的 `exit_request` 报的是**座位 3**。这正是"远端角色没挂在车上、下车布娃娃、能顶车"的来源。

## 三、五个尝试的完整记录（避免重走）

| 版本 | 改动 | 结果 |
|---|---|---|
| 0.8.0 | `avatar_rotation` 写 `true` | 朝向卡死 |
| 0.8.1 | 改 `false` | 朝向开始跟随（真进步）；机枪仍转 |
| 0.8.2 | 回程清 avatar 标志位 `0x2c` | **完全无效果**（假设被证伪） |
| 0.8.3 | 跑引擎目标座位恢复动作（`seat_action` case 1） | **完全无效果** |
| 0.8.4 | 补发引擎自己的 `entry_request` | **机枪解除绑定 ✅，但远端角色没挂上车**，下车瞬移+布娃娃+顶车 |
| 0.9.8 | 直接调用引擎入座例程 `owner_enter` | **一上车挂载就坏了**；无法切座、无法重新上车（状态损坏，非崩溃） |

> ⚠️ **0.8.4 与 0.9.8 都不要再运行。**

**结论：引擎的换座无法被分段驱动。** 任何局部调用都会让引擎权威状态与复制状态不一致，且失败模式逐次变糟。`owner_enter` 会做 `reserve`+`authority`+发 `entry_request`，但**不含挂载步骤**，单独调用 = 座位被预留、角色没挂上车。

## 五、下一步：两个低风险替代方案（研究已完成）

### 方案 A（首选）：只发 `release_request` 消息，不碰本地状态

**依据**：`release_request`（哈希 `0xc698216f`，**2 个参数**）的发送路径已定位：

- 引擎自身的发送器在 `0xba2ad0`，它是一个**逐附件循环**：遍历 `[0x3326e68+0x5748]` 个条目，筛出**类型字段 `== 0x75`** 的条目，每个用 `0x3326308` 全局管理器解析对端，然后调用通用发送器 `0xbde430` 发出 `release_request`。
- 另有**薄包装**（`0xbee3c2`、`0xb860d6`），只组装参数就调 `send`。

**为什么这是最优路径**：它是**消息**，不是本地引擎调用 —— **完全不触碰本地状态**，因此天然绕开 0.8.4/0.9.8 的损坏模式。而且语义正好对上：主机需要的正是"客人已卸下武器"这一条。

**待办**：解出这 2 个参数的构成（实体 id + 对端？），按 `entry_request` 的既有做法加 spec 记录（**不放进 `spec.core`**，带运行时字节校验），在**回程**发出。

**成功判据（客观）**：日志里回程出现 `release_request`，且**跟随其后的 `exit_request` 报的是目标座位**而不是 0.8.4 的座位 3。

### 方案 B：让引擎自己走完"离开座位 + 进入座位"

因为**动画约束已被解除**（用户明确表示"上车动画只是小问题"），引擎原生的下车/再上车路径现在是可接受的：

- 已证实引擎原生路径会发正确 RPC：下车 `exit_request→exit_accepted`，再上车 `entry_request→accepted`（0.8.4 日志里误触下车时完整出现过）；
- 但**必须整条路径一起走**，不能像 0.9.8 那样只调其中一个函数 —— 需要一个**包含挂载步骤**的入口。

**待办**：反汇编 `owner_switch`（`0x637360` 区域，是另一处 `entry_request` 调用者）与退出分支所在的函数（含 `0x1193d60..0x1193f00` 那段完整卸载链），确认哪一个**同时做本地挂载与权威通知**。

### 方案 C（保底）：收窄范围交付

**多人加强版里让武器位（机枪）不可切换**，其余六车型乘员↔乘员换座照常整合。正式版**本来就在普通模式拒绝跨区**（`normal_restriction m102 gunner -> front_passenger`），所以这不是新增限制，而是**把已有约束诚实地延伸到联机** —— 换来**机枪永远不会被留在绑定状态**，正是用户实际踩到的坑。

## 六、方法论教训（值得继承）

1. **只读探针的正确顺序**：先立住安全属性，再扩大触角。每一轮为够到更多而放宽一个保证，都必须把那个保证买回来。五个版本的失败序列：静默失败 → 看不见堆 → 崩溃 → 加门 → 门在 cdata 指针上静默失效 → 无界循环卡死 → 加上界。
2. **最终定位 `ctx` 靠的不是猜形状，而是跑引擎自己的查找**：以本地集合 id 为 key，只有 `collections` 返回的行首是**合法车型编号**（26，落在 45 分支范围内），另一个装着同样 id 的候选行首是 0。形状无法区分（三个候选同属一个容器类）。
3. **不要用 pwsh 的 `Get-Content`/`Set-Content` 管道改 UTF-8 源文件** —— 它会重新编码并吃掉引号。恢复 `build.py` 时曾因此丢失 `entry_spec`，导致 **0.9.x 全部包缺 `sync_entry_request_send`**（只跑探针所以未暴露，**联机必炸**）。现已补回并加了**构建期检查**：包里缺任一记录即让构建失败。
4. **原生内存的触角需要两道护栏**：可读性门 + 工作量上界。
